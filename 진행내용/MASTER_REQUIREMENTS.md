# 한단 산업자동화 AI Agent — 프로젝트 마스터 기준 v1.0

## 0. 문서 목적

이 문서는 한단 산업자동화 AI Agent 프로젝트의 **기준 요구사항 문서**이다.

프로젝트 규모가 크고 향후 기능이 계속 추가될 예정이므로, 개발 과정에서 기존 확정 기능이 누락되거나 임의로 축약·변경되는 것을 방지하기 위해 별도 관리한다.

### 개발 기본 원칙

1. **추가는 허용하되, 기존 확정 요구사항의 삭제·축약·구조변경은 사용자 확인 없이 하지 않는다.**
2. 코드를 수정하기 전에 영향받는 모듈을 확인한다.
3. 수정 후 기존 핵심 기능이 유지되는지 검증한다.
4. 요구사항과 설계 문서를 코드와 함께 GitHub에서 버전 관리한다.
5. 기능 종류, 제조사, 제품군 등을 코드에 과도하게 고정하지 않고 확장 가능한 열린 구조로 설계한다.
6. UI와 핵심 Agent 로직을 분리하여 향후 Streamlit에서 React 등으로 화면을 교체해도 Agent는 재사용할 수 있게 한다.

# 1. 프로젝트 정의

이 프로그램은 단순한 현장 트러블슈팅 챗봇이 아니다.

> **산업자동화 전반의 업무를 지원하는 매뉴얼·기술지식 기반 AI Agent**

를 목표로 한다.

사용 장소나 업무 목적을 현장 대응으로 한정하지 않는다.

## 1.1 현장 업무 예

- 고장 대응
- 알람 분석
- 사진/화면 분석
- 배선/설정 확인
- 파라미터 확인
- 단계별 문제 해결
- 현장 자료 분석
- 동영상 기반 동작 상태 분석

## 1.2 사무실 업무 예

- 프로그램 작성 및 검토
- 매뉴얼 조사
- 기술자료 검색
- 제품 검토 및 비교
- 설계 검토
- 자료 분석
- 기술 업무 문서화
- 특정 목적에 맞는 자료 탐색

단, **업무 종류를 위 목록으로 고정하지 않는다.**

Agent가 사용자의 요청을 해석하여 새로운 종류의 산업자동화 업무도 수행할 수 있는 열린 구조로 설계한다.

# 2. 전체 시스템 대분류

현재 기준으로 다음 9개 대분류를 사용한다.

| 번호 | 대분류 | 역할 |
|---|---|---|
| 1 | 사용자 인터페이스 | 질문, 음성, 첨부, 답변, 작업 세션 |
| 2 | Agent 판단·계획 | 의도 파악, 계획, 추가 질문, 다음 행동 |
| 3 | 지식·검색 시스템 | RAG, 매뉴얼, 사례, Semantic Cache |
| 4 | Agent 실행 도구 | 분석, 계산, 코드작성 등 확장 가능한 도구 |
| 5 | 문서 생성 | 작업 목적에 맞는 가변형 문서 생성 |
| 6 | 사용자·고객 관리 | 로그인, 고객사, 권한, 사용이력 |
| 7 | 관리자 분석 | 사용현황, 기술수요 분석, Business Insight |
| 8 | 데이터 관리 | 대화, 세션, 사례, 분석, 생성 문서 |
| 9 | 시스템/외부 연동 | Gemini, Cloud, DB, 보안, GitHub |

이 대분류는 프로젝트의 기본 골격으로 사용하고, 세부 기능은 지속적으로 추가한다.

# 3. 사용자 인터페이스

현재 Streamlit 기반 화면에서 시작하되 다음 기능을 수용한다.

- 문자 질문
- 연속 질의응답
- 음성 질문
- 필요 시 음성 답변
- PDF 업로드
- TXT 및 일반 문서 업로드
- 사진 업로드
- 스캔 이미지 업로드
- 화면 캡처 업로드
- 동영상 업로드
- 파일 Drag & Drop
- AI 답변 표시
- 대화 기록
- 작업 세션 관리
- 문서/리포트 작성 요청

현재 Streamlit UI는 초기 화면으로 활용할 수 있으나, **UI와 Agent 코드는 반드시 분리**한다.

향후 구조:

```text
Streamlit UI
     ↓
Python AI Agent
```

에서

```text
React UI
     ↓
동일 Python AI Agent
```

로 교체할 수 있어야 한다.

# 4. Agent 판단·계획

사용자의 질문을 Gemini에 바로 전달하는 단순 챗봇 구조를 사용하지 않는다.

Agent는 다음 흐름으로 동작한다.

```text
사용자 요청
     ↓
작업 목적 파악
     ↓
현재 대화 맥락 파악
     ↓
첨부자료 파악
     ↓
현재 Custom Session Set 파악
     ↓
필요 정보 판단
     ↓
부족하면 추가 질문
     ↓
필요한 자료/도구 판단
     ↓
실행 계획 수립
     ↓
필요한 Tool 실행
     ↓
결과 검토
     ↓
다음 행동 판단
     ↓
최종 답변
```

## 4.1 핵심 원칙

- 업무 종류를 미리 고정하지 않는다.
- 제조사를 미리 고정하지 않는다.
- 정보가 부족하면 임의로 단정하지 않고 추가 질문한다.
- 필요한 도구를 Agent가 업무에 따라 조합한다.
- 작업 과정에서 새로운 정보가 들어오면 계획을 동적으로 수정할 수 있어야 한다.

대상을 한단 취급 브랜드로 한정하지 않는다.

**산업자동화 관련 전 제조사와 전 제품군**을 대상으로 한다.

예:

- Mitsubishi
- Siemens
- Omron
- Yaskawa
- Rockwell
- Schneider
- Beckhoff
- Keyence
- Inovance
- Bosch Rexroth
- ABB
- Delta
- LS Electric
- 기타 향후 추가 제조사

그러나 이 목록도 코드에 고정하지 않는다.

새 제조사의 매뉴얼을 Cloud에 업로드하면 자동으로 검색 대상에 편입될 수 있어야 한다.

```text
새 매뉴얼 Cloud 업로드
        ↓
문서 분석
        ↓
제조사 / 제품군 / 모델 / 문서종류 / 버전 / 언어 등 Metadata 생성
        ↓
RAG 검색 대상 자동 편입
```

# 6. RAG 구조

Cloud에 저장된 제조사 매뉴얼과 기술자료를 기반으로 RAG 구조를 사용한다.

기본 흐름:

```text
Cloud 매뉴얼/기술자료
        ↓
문서 처리
        ↓
Metadata
        ↓
Chunking
        ↓
Embedding
        ↓
Vector DB
        ↓
Semantic Search
        ↓
관련 문서/페이지 추출
        ↓
Gemini
        ↓
근거 기반 답변
```

## 6.1 Metadata 예

- manufacturer
- product_category
- model
- document_type
- language
- version
- file_name
- document_date
- page/section
- 기타 검색 정확도 향상에 필요한 항목

## 6.2 답변 근거 관리

답변 시 가능한 경우 다음을 표시한다.

- 제조사
- 문서명
- 모델/기종
- 관련 페이지
- 관련 Section
- 매뉴얼 버전

또한 다음을 구분한다.

### 확인된 매뉴얼 근거
제조사 문서에서 직접 확인된 내용

### AI 분석/추론
매뉴얼, 대화, 첨부자료 등을 바탕으로 Agent가 분석한 내용

# 7. Semantic Cache

RAG 위에 Semantic Cache를 적용한다.

```text
사용자 질문
    ↓
Semantic Cache 확인
 ├─ 적합한 결과 있음
 │      ↓
 │   재사용 가능성 검증
 │      ↓
 │   적합하면 활용
 │
 └─ 적합한 결과 없음
        ↓
       RAG
        ↓
      Gemini
        ↓
      답변 생성
        ↓
적절한 결과를 Cache에 저장
```

단순히 질문 문장이 유사하다는 이유만으로 답변을 재사용하지 않는다.

캐시 판단에는 최소한 다음 요소를 함께 고려한다.

- 질문 의미
- 제조사
- 제품군
- 모델/기종
- 매뉴얼 버전
- 작업 목적
- 현재 Custom Session Set
- 대화 맥락
- 필요 시 고객/장비 Context

다른 모델이나 다른 매뉴얼 버전의 답변이 잘못 재사용되지 않도록 설계한다.

# 8. 동적 멀티 브랜드/기종 작업 세션
## Custom Session Set

작업 세션 시작 시 오늘 다룰 제조사와 기종을 여러 개 선택할 수 있도록 한다.

### 8.1 화면 선택

예:

```text
오늘 작업할 시스템

☑ Mitsubishi R16MTCPU
☑ Mitsubishi MR-J5
☑ Inovance SV680N
☑ STOBER Gearbox
```

### 8.2 문자 선택

예:

> 오늘은 R16MTCPU, MR-J5하고 SV680N을 사용할 거야.

Agent가 이를 인식하여 Custom Session Set을 구성한다.

### 8.3 음성 선택

동일하게 음성으로 여러 브랜드/기종을 지정할 수 있어야 한다.

### 8.4 멀티 브랜드 시스템

실제 장비는 여러 제조사 제품이 결합될 수 있으므로 한 세션에 여러 브랜드를 동시에 포함할 수 있어야 한다.

예:

```text
Mitsubishi PLC
       ↕
   EtherCAT
       ↕
Inovance Servo
       ↓
STOBER Gearbox
```

Agent는 필요할 경우 여러 제조사의 매뉴얼을 동시에 검색하고 비교할 수 있어야 한다.

# 9. Session Set 검색 원칙

Custom Session Set은 검색을 강제로 제한하는 기능이 아니라 **우선 검색 범위를 설정하는 기능**이다.

```text
1순위: Custom Session Set
        ↓ 부족
2순위: 관련 제품/연관 시스템
        ↓ 부족
3순위: 전체 매뉴얼 DB
```

작업 중 새로운 제품 정보가 들어오면 Session Set을 동적으로 추가/수정할 수 있어야 한다.

예:

> Keyence 센서도 연결되어 있어.

Agent는 현재 세션에 해당 기종을 추가할 수 있다.

## 9.1 최근 세션 재사용

이전 작업 구성을 저장하고 다시 불러올 수 있도록 한다.

예:

- A사 물류설비
- 삼성SDI 2차전지 #3라인
- 테스트 장비
- 특정 고객사 특정 설비

사용자가:

> 지난번 A사 물류설비 구성으로 시작해.

라고 하면 해당 Session Set을 다시 불러올 수 있어야 한다.

# 10. Agent 실행 도구

업무 자체를 미리 고정하지 않고, Agent가 사용할 **공통 능력(Tool)**을 확장 가능한 형태로 제공한다.

예:

- 매뉴얼 검색
- 파일 분석
- PDF 분석
- 이미지 분석
- 동영상 분석
- 코드 생성
- 코드 검토
- 계산
- 과거 사례 검색
- 자료 비교
- 데이터 분석
- 문서 생성
- 향후 외부 시스템 연동 도구

Agent는 사용자의 목적에 따라 여러 도구를 조합하여 작업한다.

예:

```text
사용자 요청
"이 서보 용량이 적당한지 검토하고 부족하면 대체품도 찾아줘."

Agent
→ 요구사항 분석
→ 매뉴얼 검색
→ 필요한 계산
→ 현재 제품 검토
→ 대체 제품 자료 검색
→ 비교
→ 결과 정리
```

# 13. 문서 생성 — 확정 요구사항

문서 형식을 몇 가지 고정 양식 중에서 선택하는 방식으로 제한하지 않는다.

> **Agent가 작업 목적 + 전체 대화 내용 + 사용자 지시를 보고 문서 형식을 결정한다.**

예:

- 고객 제출용
- 사내 기술팀 검토용
- 경영진 보고용
- 현장 기술지원 결과서
- 프로그램 개발/검토 문서
- 제품 비교 검토서
- 기술 조사 문서
- 시스템 구성 검토서
- 업무 요약
- 기타 Agent가 필요하다고 판단한 새로운 형식

동일한 작업 내용도 사용 목적에 따라 다른 형식으로 출력할 수 있어야 한다.

예:

> 고객에게 제출할 수 있게 정리해 줘.

> 우리 기술팀 내부자료로 만들어 줘.

> 대표가 볼 수 있게 한 페이지로 정리해 줘.

필요 시 PDF, DOCX 등 파일 출력 기능을 제공한다.

# 15. 관리자 시스템 — 확정 구조

관리자 시스템 상단에 **AI 경영 요약**을 제공한다.

그 아래 관리자 기능은 다음 3개 핵심 화면으로 구성한다.

## 15.1 ① 사용현황

핵심 질문:

> 누가, 언제, 무엇을 얼마나 사용했는가?

예:

- 전체 사용자 수
- 고객사별 사용자 수
- 일/주/월 사용량
- 질문 건수
- 대화 세션 수
- 업로드 자료 수
- 생성 문서 수
- 제조사별 이용현황
- 제품군별 이용현황
- 고객별 상세 사용내역
- 개별 세션 이력

## 15.2 ② 기술수요 분석

핵심 질문:

> 고객이 어떤 기술 때문에 어려움을 겪고 있는가?

분석 예:

- 반복 기술문제
- 증가하는 문의
- 고객별 주요 관심기술
- 고객별 취약기술 추정
- 기술지원 필요도
- 교육 필요도
- 문제 해결 난이도
- 반복 문의율
- 제조사별/제품별 문제 추세

고객 기술역량 Profile도 AI 분석 결과로 제공할 수 있다.

예:

```text
PLC Programming       높음
Motion                보통
EtherCAT              낮음
Servo Tuning          낮음
Robot                 보통
```

단, 이는 확정 평가가 아니라 **사용 데이터를 기반으로 한 AI 추정**임을 표시한다.

## 15.3 ③ Business Insight

핵심 질문:

> 그래서 한단이 무엇을 해야 하는가?

분석 분야:

- 기술지원 Opportunity
- 교육 Opportunity
- 제품 Opportunity
- 솔루션 Opportunity
- 신규 프로젝트 신호
- 대체품/교체 수요
- 고객 관심 변화
- 영업 Follow-up 필요 고객

예:

```text
A사
EtherCAT 문의 반복
→ EtherCAT 실무교육 제안

B사
Servo Tuning 문의 반복
→ 현장 Tuning 기술지원 제안

C사
다축 Motion/Cam/Gear 문의 증가
→ Motion Controller 솔루션 검토

D사
백래시/반복정밀도 문제 지속
→ 고정밀 감속기 검토
```

# 17. 관리자 분석의 신뢰성 원칙

AI가 추정한 내용을 사실처럼 표시하지 않는다.

분석 화면에서 다음 세 단계를 구분한다.

### 확인된 데이터

예:

> 최근 90일 EtherCAT 관련 질문 31건

### AI 분석

예:

> 신규 EtherCAT 적용 과정에서 기술적 어려움이 발생하고 있을 가능성이 높음

### 추천 행동

예:

> EtherCAT 실무교육 또는 초기 프로젝트 기술지원 검토

**사실 → 분석 → 제안** 구조를 관리자 분석의 공통 원칙으로 사용한다.

# 18. 고객 기술수요 분석의 상세 목적

단순히 "질문이 많다"는 통계를 제공하는 수준을 넘어선다.

다음 의사결정에 활용할 수 있어야 한다.

## 18.1 필요한 기술지원 판단

- 반복 문의 유형
- 해결까지 걸리는 대화 수
- 동일 문제 재발
- 특정 제조사/기종에 집중된 문제
- 현장 방문 필요 가능성
- 표준 프로그램/Template 제공 필요성

## 18.2 필요한 교육 판단

예:

- EtherCAT 교육
- Servo Tuning 교육
- Motion Programming 교육
- PLC Communication 교육
- Robot Programming 교육

교육 필요도를 고객별로 분석하고, 판단 근거를 함께 제시한다.

## 18.3 제품/솔루션 제안 판단

기술적 문제와 제품을 연결하여 분석한다.

단순히 질문이 많다는 이유로 제품을 추천하지 않고, 고객의 실제 문제와 요구를 근거로 제안한다.

예:

```text
다축 동기제어 문의 증가
+ Cam/Gear 질문 증가
+ PLC 성능 관련 문의
→ 고성능 Motion Controller 검토 가능성
```

또는:

```text
백래시
+ 반복 위치정밀도
+ 정·역 운전 문제
→ 고정밀 감속 솔루션 검토 가능성
```

# 20. 관리자 3개 화면의 연결

3개 화면은 독립된 통계 페이지가 아니라 서로 Drill-down할 수 있어야 한다.

```text
③ Business Insight
      ↓
"왜 그렇게 판단했는가?"
      ↓
② 기술수요 분석
      ↓
"근거 데이터가 무엇인가?"
      ↓
① 사용현황 / 실제 세션
```

대표자가 Business Insight에서 제안을 보고, 기술수요 분석을 거쳐 실제 사용 근거까지 확인할 수 있도록 한다.

# 22. 프로그램 구조 원칙

현재 `app.py` 하나에 모든 기능을 계속 추가하지 않는다.

역할별 구조를 기본으로 한다.

예:

```text
handan-ai-agent/
│
├─ app.py
│
├─ ui/
├─ agent/
├─ knowledge/
├─ tools/
├─ reports/
├─ users/
├─ analytics/
├─ database/
├─ services/
├─ config/
├─ tests/
└─ docs/
```

세부 파일은 실제 구현에 필요한 만큼 점진적으로 추가한다.

핵심 원칙:

> 화면은 화면끼리  
> Agent는 Agent끼리  
> 검색은 검색끼리  
> 분석은 분석끼리  
> 데이터는 데이터끼리 분리한다.

# 25. 앞으로 기능을 추가하는 방법

사용자가 새로운 아이디어나 기능을 생각했을 때 다음과 같이 요청한다.

> **"AI Agent 요구사항에 이것 추가하자: ○○○"**

이 경우 바로 코드를 수정하지 않고 먼저 다음을 검토한다.

1. 기존 요구사항과 충돌하는가?
2. 어느 대분류에 들어가는가?
3. 기존 구조 변경이 필요한가?
4. 다른 기능에 어떤 영향을 주는가?
5. 새로운 데이터가 필요한가?
6. 보안/권한에 영향이 있는가?
7. 요구사항 문서의 어느 버전에 반영할 것인가?

검토 후 요구사항에 추가한다.

# 27. 변경 금지 원칙

프로젝트 장기 안정성을 위해 다음을 핵심 규칙으로 한다.

> **새로운 기능 추가를 이유로 기존 확정 기능을 임의로 삭제·축약하거나 다른 구조로 변경하지 않는다.**

기존 확정 요구사항을 변경할 필요가 있을 경우 반드시 사용자에게 먼저 설명하고 확인을 받는다.

또한 한 기능을 수정했을 때 같은 맥락의 다른 기능에 오류가 발생하지 않는지 전체적으로 검수한다.
